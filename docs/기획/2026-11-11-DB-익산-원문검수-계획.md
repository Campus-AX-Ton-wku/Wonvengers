# Perky DB — 익산 원문·검수 계획 (확정)

확정일: 2026-11-11 · 담당: 노찬영 · 박민준 · 리뷰: ggue
목표: **11/17 멘토 최종 점검**에서 "원문을 그대로 보관하고, 누가 언제 확인했는지 남긴다"를 실제 DB로 보여준다.
Word 판: `Perky_DB_익산_원문검수_계획.docx` (같은 내용)

> 이 문서가 11/9 「DB 적재 체크리스트」(전체 이관 · DB→JSON 내보내기 · 앱 반영)를 **대신한다**.
> 그 방식은 쓰지 않는다. 표 설계 설명은 [2026-11-09-DB-재설계-5테이블.md](2026-11-09-DB-재설계-5테이블.md).

## 정한 방식

- **앱은 지금처럼 정책 JSON(`apps/web/data`)을 읽는다.** 앱 코드는 바뀌지 않는다.
- **Supabase에는 익산 사용자에게 보이는 14건 + 새 후보 2건만** 넣는다 — 원문, 검수 기록, 가공 정책, 연락처.
- 값이 틀린 걸 찾으면 **JSON은 ggue가 PR로 고치고**, DB에는 같은 값과 검수 기록을 남긴다.
- 사용자 데이터는 **AWS**(ggue의 카카오 로그인, DynamoDB `UserData`)가 맡는다 → Supabase에는 사용자 표가 없다.
- 신뢰도: ggue의 11/3 원문 재대조를 첫 확인으로 넣고("JSON 검수일 이관"이라고 표시), 우리가 한 번 더 확인하면
  서로 다른 두 사람 → **"교차검수"**.

## ⛔ 절대 하지 말 것

> [!CAUTION]
> 아래는 이 작업 내내 지킨다. 헷갈리면 하지 말고 단톡에 먼저 묻는다.

### 앱과 정책 JSON

1. **이 작업 중에 앱 코드(`apps/web`)와 정책 JSON(`apps/web/data`)을 건드리지 않는다.**
   → 앱은 지금 그대로 JSON을 읽는다. 시연이 깨지지 않게 하는 게 이번 방식의 핵심이다.
2. **앱이 Supabase를 읽게 바꾸지 않는다.**
   → Supabase는 멘토 점검용 기록 창고다. 시연 중 서버가 멈추면 앱도 멈춘다.
3. **DB 값을 JSON에 덮어쓰지 않는다 (내보내기 안 함).**
   → JSON이 원본이다. 고칠 값은 ggue가 PR로 JSON에서 고친다.
4. **JSON과 DB 중 한쪽만 고치지 않는다.**
   → 틀린 값은 ① 검수 기록에 "불일치" → ② ggue가 JSON 수정 → ③ DB도 같은 값으로. 셋이 한 묶음이다.
5. **새 후보 2건(주소전입 학생 지원 · 전입장려금)을 바로 JSON에 넣지 않는다.**
   → 익산시 원문 확인 + 팀 합의 뒤에 ggue가 넣는다. 그 전까지는 DB에만 상태 "보류"로.

### DB 기록

6. **확인하지 않은 값을 추정해서 넣지 않는다.**
   → 모르면 비워 두고 메모에 "확인 필요". 그럴듯한 숫자가 이 앱에서 가장 큰 사고다.
7. **AI(GPT·Claude)가 준 값을 DB나 JSON에 바로 넣지 않는다.**
   → AI는 원문 요약과 교차 확인용이다. 넣는 값은 사람이 원문에서 확인한 것만.
8. **자기가 고친 값을 자기가 검수하지 않는다.**
   → 작성자 ≠ 검수자. DB가 막지만, 막기 전에 지킨다.
9. **원문 표와 검수 기록을 고치거나 지우지 않는다.**
   → 틀렸으면 새 행으로 다시 남긴다. 기록이 남아 있어야 멘토에게 보여줄 수 있다.
10. **다른 사람 이름으로 기록하지 않는다.**
    → Table Editor에서 고칠 때 `edited_by`는 본인 이름. ggue의 11/3 재대조는 "JSON 검수일 이관"이라고 밝혀서 넣는다.
11. **전화 답을 추측으로 채우지 않는다.**
    → 공식 답이 아니면 "담당자 개인 의견", 모르면 "모름".
12. **익산 범위(16건) 밖 정책을 DB에 넣지 않는다.**
    → 시연 전에는 범위를 늘리지 않는다. 늘리고 싶으면 11/17 이후에 다시 정한다.

### 보안

13. **API 키 · Supabase DB 비밀번호 · secret 키를 단톡 · 문서 · GitHub · 스크린샷에 올리지 않는다.**
    → 키는 각자 `apps/web/.env.local`에만(git 제외). 필요한 사람은 각자 발급받는다.
14. **Supabase secret 키(예전 이름 service_role)를 코드에 넣지 않는다.**
    → 이 DB는 익명 접근이 전부 막혀 있다. 팀원은 대시보드에 로그인해서 쓴다.

### git · Supabase 작업

15. **develop · main에 직접 push하지 않는다.**
    → 항상 `feature/supabase-db` 브랜치 → PR → ggue 리뷰 → 머지. 작업 전에 `git pull`.
16. **옛 설계(11/2, 표 11개)를 다시 꺼내 적용하지 않는다.**
    → 11/11에 저장소에서 지웠다(git 기록에만 남음). 적용할 SQL은 `supabase/redesign/` 하나.
17. **이관 데이터(seed)를 두 번 실행하지 않는다.**
    → 중복 오류가 난다. 다시 넣으려면 표를 비운 뒤에.

## 원문 대조 방법 (둘이 똑같이)

1. **원문 열기**: 데이터의 원문 주소. 링크가 죽었으면 기관 홈페이지 공고에서 사업명으로 검색
2. **사본 보관**: PDF·캡처를 Storage `source-files/<정책id>/`에, 본문 글자는 원문 표에 (종류 "공고문")
3. **대조**: 나이 · 지역 · 소득(세전/세후) · 재산 · 무주택 · 보증금·월세 상한 · 면적 · 금액 · 신청 기간·인원 · 신청 방법 · 문의처 · 중복 수급 · 연세 인정
4. **AI 교차**: 같은 원문·같은 프롬프트를 GPT와 Claude에 → 둘이 다른 칸만 원문으로 다시 확인 (AI 값은 바로 넣지 않는다)
5. **검수 기록 남기기** (SQL Editor)
   ```sql
   insert into policy_checks (policy_id, method, result, checked_by, memo)
   values (<id>, '원문대조', '일치', '본인 이름', '공고 2쪽 표');
   ```
6. **틀렸으면**: 결과를 '불일치'로 남기고 ggue에게 JSON 수정 요청 → JSON이 고쳐지면 DB도 같은 값으로
   (`edited_by`에 본인 이름, `edit_note`에 원문 위치)
7. **모르는 값**은 비워 두고 메모에 "확인 필요"

AI 교차 프롬프트:

```
아래는 [기관]의 [정책명] 공고 원문이다. 원문에 적힌 내용만 사용해서 표를 채워라.
원문에 없는 항목은 추측하지 말고 "원문에 없음"이라고 써라. 각 칸마다 근거 문장을 그대로 인용해라.
항목: 나이(만, 기준일) / 거주 지역 / 소득(청년가구·원가구, 중위 %, 세전·세후) / 재산 / 무주택 /
보증금·월세 상한 / 면적 제한 / 지원 금액(월 상한·개월·총액) / 신청 기간 / 모집 인원·선착순 /
신청 방법 / 문의처 / 중복 수급 / 연세 인정 여부
[원문 붙여넣기]
```

## 부록 C. 자주 막히는 곳

| 증상 | 해결 |
|---|---|
| `npm test`가 "node를 찾을 수 없음" | `node redesign.test.mjs`처럼 node로 직접 실행 |
| API가 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` | 승인 직후라 아직 등록 전. 몇 시간 뒤 다시 |
| `invalid input value for enum opt_...` | 정해진 값이 아님. 드롭다운에서 고른다 |
| `violates check constraint "나이_범위"` 같은 한글 규칙 이름 | 값이 규칙에 어긋남. 원문을 다시 본다 |
| 수정이 `고친_이유_필수`로 거부 | `edit_note`에 고친 이유와 원문 위치를 새로 적는다 |
| 검수가 `작성자_검수자_같음`으로 거부 | 그 버전을 고친 사람이 아닌 다른 팀원이 확인한다 |
| seed 실행 시 `duplicate key` | 이미 들어가 있다. 두 번 실행하지 않는다 |
