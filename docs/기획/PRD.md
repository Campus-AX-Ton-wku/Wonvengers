## 1. 제품 요약

> # “이 방에 살면, 지원금을 반영해 내가 실제로 얼마를 내야 할까?”

사용자가 계약 조건과 정책 판정에 꼭 필요한 정보를 입력하면, 앱은 청년 주거지원 정책을 규칙 기반으로 판정하고 다음을 한 화면에 보여준다.

1. 입력한 조건에서 검토할 수 있는 **최대 지원 가능액**
2. 최대 지원 가능액을 반영한 **최종 예상 주거비**
3. 정책별 충족·확인 필요·대상 아님 요건
4. 정책별 공식 출처와 신청 링크

이 제품의 핵심은 정책을 많이 보여주는 것이 아니라, **근거가 확인된 정책만 최종 금액에 반영하는 것**이다.

## 2. 배경 및 문제 정의

### 2-1. 핵심 문제

청년 주거지원 정책은 나이와 소득만으로 판정되지 않는다. 정책에 따라 다음 조건이 함께 사용된다.

- 가구원 수와 본인 가구·원가구의 소득
- 본인 가구·원가구의 재산과 자동차 등 자산 기준
- 기초생활수급자·차상위계층 등 복지 자격
- 무주택 여부와 부모 동거 여부
- 학생·취업·독립가구 여부
- 거주 지역, 전입신고, 임대차계약 명의
- 보증금·월세 상한, 계약 기간, 지급 가능 개월 수
- 다른 주거급여·월세지원과의 중복 수급 여부

기존 기획처럼 **나이·연소득·재학 여부 3개만 입력받아 지원액을 합산하면**, 실제로는 받을 수 없는 정책까지 포함할 수 있다. 사용자가 그 금액을 믿고 계약하면 자금 계획이 어긋난다.

### 2-2. 이번 개정의 결정

2주 안에 여러 문제를 얕게 다루지 않는다. 다음 한 가지 흐름을 완성한다.

> **주거비 입력 → 정책별 필수 조건 확인 → 적용 가능성 판정 → 중복 제한 반영 → 최종 예상 금액 → 신청 연결**

계약 안전, 집 상태, 시세 비교, 매물 탐색은 모두 MVP에서 제외한다. 남은 제작 시간은 정책 조건 조사, 판정 규칙, 금액 계산, 테스트에 사용한다.

### 2-3. 정확성 원칙

앱은 행정기관의 최종 심사를 대신할 수 없다. 따라서 화면에서 “확정 지급액”이라고 표현하지 않고, **“입력값과 공식 조건에 따른 최대 지원 가능액”**이라고 표현한다.

다만 최대 가능액이 무제한 합산되거나 확정액처럼 보이지 않도록 아래 규칙을 지킨다.

- 모든 필수 조건을 입력했고 규칙을 통과한 정책은 **예상 적용**으로 분류한다.
- 사용자가 `모름`을 선택했거나 앱이 판정할 수 없는 조건이 하나라도 있으면 **조건 충족 시 가능**으로 분류한다.
- 최대 지원 가능액에는 예상 적용 정책과 조건 충족 시 가능 정책 중 **동시에 성립 가능한 최대 조합**을 반영한다.
- 중복 제한 또는 서로 양립할 수 없는 자격 조건이 있는 정책은 동시에 합산하지 않는다.
- 대상 아님·신청 불가 정책의 금액은 최대 지원 가능액에서 제외한다.
- 대출·보증·저축 상품은 갚아야 하거나 현금 지원이 아니므로 지원금 합계에서 제외한다.
- 마감된 정책은 예상 적용으로 분류하지 않는다.
- 금액 요약에는 **최대 지원 가능액**과 **최종 예상 주거비** 두 개만 표시한다. 조건별 금액을 별도 층으로 나누지 않는다.

### 2-4. 매물 정보와 API에 대한 제품 결정

MVP는 부동산 플랫폼처럼 현재 광고 중인 매물 DB를 직접 제공하지 않는다. 사용자가 중개사·부동산 앱·임대인에게 받은 **해당 매물의 계약 조건을 직접 입력**하는 방식을 기준으로 한다.

국토교통부 실거래가 API는 현재 매물이 아니라 이미 신고된 과거 전월세 계약을 제공한다. 전세·월세 구분과 보증금·월세 등의 신고값은 확인할 수 있지만, **연세 여부는 별도 표준 항목으로 제공되지 않는다.** 특히 단독·다가구는 개인정보 보호를 위해 지번 일부만 공개되므로, 원광대 인근의 특정 원룸 광고와 정확히 결합할 수 없다. 따라서 실거래가는 해당 매물의 값이 아니라 **주변 참고 사례**로만 사용한다.

건축물대장 API는 주소가 확보된 경우 건물 용도·면적·층·건축연도 등을 보강할 수 있지만, 현재 공실 여부·광고 가격·관리비·연세 선납 조건은 제공하지 않는다.

정책 API도 사용자와 매물 정보를 보내면 자격과 지원액을 완성해 주는 형태가 아니다. 온통청년 API는 지역·분류·키워드에 맞는 정책을 찾고 기본 설명을 가져오는 **정책 후보 탐색용**으로 사용하고, 최종 판정 조건과 금액 계산식은 공식 공고를 검수해 앱의 규칙 데이터로 관리한다.

> 사용자 경험은 “한 번 입력하면 한 번에 결과를 본다”로 만들 수 있다. 다만 기술적으로는 단일 API가 모든 정보를 반환하는 것이 아니라, **사용자 입력 + 검수된 정책 데이터 + 자체 판정 엔진**을 앱이 결합하는 구조다.

## 3. 목표와 성공 기준

### 3-1. 제품 목표

사용자가 하나의 실제 또는 가상 계약 조건을 입력한 뒤, 자신에게 적용될 가능성이 높은 주거지원과 이를 반영한 최종 예상 주거비를 이해하고 공식 신청 페이지로 이동하게 한다.

### 3-2. 발표 성공 기준

| 구분 | 기준 | 목표 |
|---|---|---|
| 핵심 흐름 | 입력 → 조건부 질문 → 판정 → 최종 금액 → 신청 링크를 끊김 없이 시연 | 필수 |
| 정책 범위 | 공식 자료로 조건과 계산식을 검증한 직접 지원 정책 | **3~5개** |
| 판정 정확도 | 공식 예시·경계값·팀 작성 테스트 시나리오의 기대 결과와 일치 | **100%** |
| 조합 정확도 | 대상 아님·신청 불가·중복 불가 정책이 최대 조합에 포함되지 않음 | 필수 |
| 금액 이해도 | 결과 상단에 최대 지원 가능액과 최종 예상 주거비만 표시 | 필수 |
| 설명 가능성 | 모든 판정에 통과 조건 또는 탈락·미확인 이유가 표시됨 | 필수 |
| 출처 | 모든 정책에 공식 출처와 확인 날짜 표시 | 필수 |
| 배포 | 모바일에서 접근 가능한 배포 URL | 필수 |

### 3-3. 비목표

- 전국의 모든 청년정책 수집
- 부동산 매물 목록과 시세 적정성 비교
- 민간 부동산 사이트 크롤링 또는 비공식 API 연동
- 계약 안전·등기·하자 확인 기능
- 계약 전 준비 항목 제공
- 대출 가능 금액을 지원금처럼 합산
- 정책 신청 대행 또는 승인 보장
- 회원가입, 사용자 DB, 서류 업로드
- AI를 이용한 자격 판정 또는 금액 계산
- 법률·금융 자문

## 6. 기능 요구사항

### F1. 주거비·계약 조건 입력

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F1-1 | 거주 예정 지역을 시·군·구 단위로 입력받는다 | 필수 |
| F1-2 | 계약형태를 월세·연세 중 선택하게 한다 | 필수 |
| F1-3 | 보증금, 월세 또는 연세 선납액, 월 관리비를 입력받는다 | 필수 |
| F1-4 | 선정 정책이 이사비·중개보수 등을 지원하면 해당 일시 지출을 추가로 입력받는다 | 필수 |
| F1-5 | 계약 시작 예정일과 거주 예정 개월 수를 입력받는다 | 필수 |
| F1-6 | 연세는 월 환산액(`연세액 ÷ 계약 개월 수`)을 함께 표시한다 | 필수 |
| F1-7 | 관리비는 월세지원 대상 금액에 자동 포함하지 않는다 | 필수 |
| F1-8 | 금액 단위와 입력 오류를 즉시 검증한다 | 필수 |
| F1-9 | 입력값의 출처를 부동산 광고·중개사 안내·계약서 중 선택하게 한다 | 필수 |
| F1-10 | 사용자가 “해당 매물의 실제 계약 조건과 일치함”을 확인한 뒤 계산을 시작한다 | 필수 |
| F1-11 | 발표용 예시 매물은 팀이 직접 확인한 고정 데이터이며 실제 매물·실거래 사례 여부를 표시한다 | 필수 |

### F2. 정책 판정용 조건부 질문

#### F2-1. 공통 입력

| 구분 | 필수 입력 |
|---|---|
| 본인 | 생년월일, 학생·재직 등 현재 상태 |
| 거주 | 현재·예정 거주 지역, 부모와 별도 거주 여부, 전입신고 가능 여부 |
| 주택 | 무주택 여부, 계약자 명의가 본인인지 여부 |
| 가구 | 본인 가구원 수, 혼인 여부, 원가구 적용 여부 |
| 소득·재산 | 본인 가구와 필요한 경우 원가구의 월 소득 또는 공식 소득구간, 정책이 요구하는 재산 기준 충족 여부 |
| 복지 자격 | 기초생활수급자, 차상위계층, 주거급여 수급 여부 |
| 중복 수급 | 현재 받고 있거나 신청 중인 월세·주거비 지원 |

#### F2-2. 정책별 추가 질문

공통 답변으로 정책 후보를 먼저 좁힌 뒤, 남은 후보의 `required_inputs` 중 아직 답하지 않은 항목만 추가로 묻는다.

- 지역·나이 등에서 이미 탈락한 정책을 위한 추가 질문은 표시하지 않는다.
- 서로 다른 정책이 같은 정보를 요구하면 한 번만 묻고 답변을 공유한다.
- “소득 요건을 충족하는가?”처럼 계산 결과를 사용자에게 묻지 않는다. 가구원 수와 소득을 입력받아 앱이 판정한다.
- 기초생활수급 여부, 본인 명의 계약, 다른 지원 수급 여부처럼 사용자가 아는 사실은 예·아니오·모름으로 묻는다.
- 행정기관의 증빙 심사가 필요한 항목은 답변 여부와 관계없이 결과에 확인 방법을 함께 표시한다.

#### F2-3. 입력 방식

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F2-1 | 모든 질문에는 사용자가 판단할 수 없는 경우를 위한 `모름` 선택지를 제공한다 | 필수 |
| F2-2 | 앞선 답변에 따라 필요한 후속 질문만 노출한다 | 필수 |
| F2-3 | 각 질문에 “왜 필요한가”와 확인 방법을 한 문장으로 안내한다 | 필수 |
| F2-4 | 소득·재산 기준은 정책 기준연도의 중위소득·자산 상한 표와 가구원 수를 이용해 계산한다 | 필수 |
| F2-5 | 정책이 공식 소득인정액을 요구하고 사용자가 이를 모르면 임의 추정하지 않는다 | 필수 |
| F2-6 | 입력값은 브라우저에만 저장하고 서버로 전송하지 않는다 | 필수 |
| F2-7 | 결과 화면에서 답변을 수정하고 즉시 다시 계산할 수 있다 | 필수 |
| F2-8 | 후보 정책들의 추가 질문을 합쳐 중복 질문을 제거한다 | 필수 |
| F2-9 | 후보에서 제외된 정책의 전용 질문은 사용자에게 묻지 않는다 | 필수 |

> 질문 수를 억지로 고정하지 않는다. 대신 선택한 정책을 판정하는 데 필요하지 않은 질문은 보여주지 않는다. **짧은 설문보다 틀리지 않는 판정이 우선**이다.

### F3. 규칙 기반 자격 판정

#### F3-1. 판정 상태

각 정책은 다음 네 상태 중 하나로 분류한다.

| 상태 | 기준 | 최대 가능액 반영 |
|---|---|---|
| **예상 적용** | 앱이 확인하는 필수 조건을 모두 입력했고 모두 통과 | 포함 |
| **조건 충족 시 가능** | `모름`, 증빙 필요, 앱이 계산할 수 없는 조건이 하나 이상 존재 | 최대 가능 조합 후보 |
| **대상 아님** | 필수 조건 중 하나 이상 불충족 | 제외 |
| **신청 불가** | 신청 기간 종료, 예산 소진 확인, 대상 지역 아님 | 제외 |

#### F3-2. 판정 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F3-1 | 판정과 금액 계산은 모두 코드에 정의된 결정론적 규칙으로 수행한다 | 필수 |
| F3-2 | 같은 입력과 같은 정책 버전은 항상 같은 결과를 반환한다 | 필수 |
| F3-3 | 예상 적용 정책에는 통과한 핵심 조건을 표시한다 | 필수 |
| F3-4 | 조건 충족 시 가능 정책에는 확인하지 못한 조건과 확인 방법을 표시한다 | 필수 |
| F3-5 | 대상 아님 정책에는 최초 탈락 이유뿐 아니라 모든 탈락 이유를 표시한다 | 필수 |
| F3-6 | 정책별 신청 기간과 현재 신청 가능 여부를 판정한다 | 필수 |
| F3-7 | 중복 제한 정책을 동시에 합산하지 않는다 | 필수 |
| F3-8 | 가능한 조합 중 최대 지원 가능액이 가장 큰 유효 조합을 기본 추천한다 | 필수 |
| F3-9 | 정책별 공식 출처, 확인 날짜, 적용 기준연도를 표시한다 | 필수 |

#### F3-3. 금액 계산 원칙

계산 기간은 사용자가 입력한 거주 예정 기간으로 하되, 기본 결과는 최대 12개월 기준으로 보여준다. 보증금은 반환을 전제로 하는 목돈이므로 총 지출에서 빼지 않고 계약 시 필요 현금에만 표시한다.

정책별 예상액은 정책마다 정의한 계산식을 사용한다.

```text
계산 기간 명목 총 지출 = (월 환산 임대료 + 월 관리비) × 계산 개월 수
                         + 입력한 일시 주거 지출

월 지원형 총 예상액 = min(정책 월 상한, 정책이 인정하는 실제 월세)
                       × 지급 가능 개월 수
일시 지원형 총 예상액 = min(정책 총 상한, 정책이 인정하는 실제 지출)

최대 지원 가능액 = 예상 적용·조건 충족 시 가능 정책 중
                    중복 제한과 자격 조건을 위반하지 않는 최대 조합의 총액
최종 예상 주거비 = max(0, 명목 총 지출 - 최대 지원 가능액)
```

다음 항목은 정책별로 별도 처리한다.

- 지급 개월 수와 계약 기간 중 더 짧은 기간
- 신청일·계약 시작일에 따른 첫 지급 가능 월
- 월세 인정 범위와 관리비 제외 여부
- 보증금 또는 월세 상한
- 소급 지급 여부
- 중복 수급 시 전액 제외 또는 차액 지급 규칙

### F4. 결과와 신청 연결

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F4-1 | 정책을 예상 적용·조건 충족 시 가능·대상 아님·신청 불가로 나누어 표시한다 | 필수 |
| F4-2 | 각 정책에 충족·미충족·확인 필요 요건을 표 형태로 표시한다 | 필수 |
| F4-3 | 정책별 지원 형태, 적용 산식, 지급 기간 또는 지급 시점, 총 예상액을 표시한다 | 필수 |
| F4-4 | 결과 상단에는 **최대 지원 가능액**과 **최종 예상 주거비** 두 금액만 크게 표시한다 | 필수 |
| F4-5 | 중복 제한으로 제외한 정책과 선택한 최적 조합을 표시한다 | 필수 |
| F4-6 | 계약 시 필요한 선납액과 지원금 지급 시점을 분리해 표시한다 | 필수 |
| F4-7 | 월 단위 지원은 계약 당일 필요한 목돈을 줄이지 않는다고 안내한다 | 필수 |
| F4-8 | 조건 충족 시 가능 정책이 최대 지원 가능액에 포함되면 해당 미확인 조건을 금액 바로 아래에 표시한다 | 필수 |
| F4-9 | 정책별 공식 신청 페이지를 새 탭으로 연결한다 | 필수 |
| F4-10 | 결과 기준일과 정책 데이터 확인 날짜를 표시한다 | 필수 |
| F4-11 | 결과를 모바일에서 캡처하기 쉬운 한 화면 요약으로 제공한다 | 권장 |

결과 화면에는 다음 문구를 항상 표시한다.

> 최대 지원 가능액은 입력값을 바탕으로 조건 충족 시 받을 수 있는 상한을 계산한 값입니다. 실제 소득인정액, 제출 서류, 예산 상황 등에 따라 지원액이 더 적거나 없을 수 있으며 최종 자격과 지급액은 해당 기관이 결정합니다.

## 8. 정책 선정 기준

### 8-1. MVP에 포함할 정책

다음 조건을 모두 만족하는 직접 지원 정책을 **3~5개만** 선정한다.

1. 1차 사용자 또는 익산 지역 청년에게 실제로 관련이 있다.
2. 발표 기준 신청 가능하거나, 다음 모집 일정과 조건이 공식 공고로 확인된다.
3. 자격 조건과 금액 계산식이 공식 문서에 명시되어 있다.
4. 필요한 입력을 사용자가 답하거나 `모름`으로 표시할 수 있다.
5. 공식 신청 페이지가 있다.

### 8-2. MVP에서 제외할 정책

- 대출·보증·청약·저축처럼 직접 지급 지원금이 아닌 상품
- 신청이 끝났고 재개 일정이 확인되지 않은 사업
- 심사 기준이 비공개이거나 정량 규칙으로 옮길 수 없는 사업
- 공식 공고와 신청 링크를 확인하지 못한 사업
- 1차 사용자와 관련성이 낮은 타 지역 정책

정책 수를 늘리기보다 **정책별 조건·예외·금액·중복 관계를 끝까지 검증하는 것**을 완료 기준으로 삼는다.

## 9. 데이터 및 API 설계

### 9-1. 매물·정책 데이터 원천과 한계

| 데이터 원천 | 얻을 수 있는 정보 | 얻을 수 없는 정보 | MVP 사용 방식 |
|---|---|---|---|
| **사용자 입력** | 현재 보고 있는 매물의 보증금·월세/연세·관리비·계약기간 | 입력이 사실인지 자동 검증 | **계산의 기준값** |
| [국토부 단독·다가구 전월세 실거래가 API](https://www.data.go.kr/data/15126472/openapi.do) | 지역·계약일·전월세 구분·보증금·월세 등 과거 신고 정보 | 현재 광고 매물, 정확한 단독·다가구 지번, 공실·관리비·연세 여부 | 발표 전 익산 참고 사례를 정적 JSON으로 수집 |
| [국토부 건축HUB 건축물대장 API](https://www.data.go.kr/data/15134735/openapi.do) | 주소 기반 용도·면적·층·건축연도 등 | 임대가격, 공실, 관리비, 실제 계약조건 | MVP 이후 주소 입력 보조 기능 후보 |
| [온통청년 청년정책 API](https://www.data.go.kr/data/15143273/openapi.do) | 지역·분류·키워드별 정책 목록과 설명 | 사용자별 최종 자격, 구조화된 모든 예외, 최종 지원액 | 정책 후보 발견·갱신 확인용 |
| **정책 공식 공고문** | 자격·예외·금액·기간·중복 제한 | 사용자의 실제 증빙 결과 | 정책 규칙 데이터의 최종 근거 |

2026-08-12 공식 공공 API 조사 범위에서는 현재 광고 중인 민간 전월세 매물을 통합 제공하는 API를 확인하지 못했다. 민간 부동산 사이트를 크롤링하거나 비공식 API를 사용하는 방식은 약관·안정성·구현기간 문제가 있으므로 MVP에서 제외한다.

### 9-2. “한 번에 계산” 처리 구조

```text
사용자가 입력한 매물 조건
        +
공통 자격 답변
        ↓
지역·나이 등으로 정책 후보 선별
        ↓
후보 정책들의 required_inputs 합집합 생성
        ↓
중복을 제거한 정책별 추가 질문
        ↓
검수된 정적 정책 규칙으로 자격·금액·중복 판정
        ↓
정책별 요건표 + 최대 지원 가능액 + 최종 예상 주거비
```

MVP의 계산 시점에는 외부 API를 필수 호출하지 않는다. 실거래 참고값과 정책 후보는 발표 전에 수집·검수해 정적 JSON으로 저장한다. 이렇게 하면 API 장애·호출 제한·정책 원문 변경이 있어도 같은 입력에 같은 결과를 보장할 수 있다.

### 9-3. 정책 스키마

| 필드 | 설명 |
|---|---|
| `id`, `name`, `agency` | 정책 식별자, 이름, 주관기관 |
| `region_scope` | 적용 지역 |
| `application_start`, `application_end` | 신청 기간 |
| `benefit_type` | 월세지원·이사비 등 직접 지원 유형 |
| `required_inputs` | 판정에 필요한 사용자 입력 목록 |
| `eligibility_rules` | 나이·가구·소득·재산·복지 자격·주택·계약 조건 규칙 |
| `exception_rules` | 수급자 예외, 원가구 미적용 등 예외 규칙 |
| `benefit_formula` | 월 상한, 인정 월세, 지급 개월 수, 총액 계산식 |
| `payment_schedule` | 월 지급·일시 지급, 첫 지급 시점 |
| `exclusive_group` | 동시에 합산할 수 없는 정책 그룹 |
| `source_url` | 공식 공고 또는 공식 안내 페이지 |
| `apply_url` | 공식 신청 페이지 |
| `verified_at`, `effective_year` | 마지막 확인일과 적용 기준연도 |
| `notes` | 증빙·예산 소진·기관 확인이 필요한 내용 |

### 9-4. 기준표 데이터

정책과 별도로 기준연도별 중위소득, 가구원 수별 상한 등 공통 기준표를 관리한다. 정책 규칙에 숫자를 중복 하드코딩하지 않는다.

```text
data/
  sample-listings.json
  nearby-rent-transactions.json
  policies.json
  income-thresholds.json
  policy-test-cases.json
```

### 9-5. 검증 절차

정책 한 건은 다음 절차를 모두 마쳐야 앱에 노출할 수 있다.

1. 공식 공고문과 공식 신청 안내를 확보한다.
2. 모든 자격 조건·예외·금액·기간·중복 제한을 구조화한다.
3. 작성자 외 팀원 1명이 원문과 구조화 데이터를 교차 검수한다.
4. 최소·최대 경계값과 대표 사례를 테스트로 작성한다.
5. 테스트를 통과한 뒤 `verified_at`을 기록한다.

블로그, 뉴스 기사, 요약 게시물은 정책 발견용으로만 사용하고 최종 근거로 사용하지 않는다.

```text
  policy-test-cases.json
```

서버, 데이터베이스, AI API는 MVP에 필요하지 않다. 개인정보와 소득 정보는 브라우저 밖으로 보내지 않는다.

## 11. 테스트 및 완료 조건

### 11-1. 필수 테스트

| 영역 | 테스트 |
|---|---|
| 자격 | 나이·소득·재산·보증금·월세의 최소/최대 경계값 |
| 예외 | 기초생활수급자·차상위계층·원가구 미적용 등 정책별 예외 |
| 미확인 | 필수 입력이 `모름`이면 조건 충족 시 가능으로 분류 |
| 기간 | 신청 시작 전·기간 중·마감 후 분류 |
| 금액 | 월 상한, 실제 월세 상한, 계약 개월 수, 소급 지급 여부 |
| 중복 | 배타 정책 동시 합산 방지와 최적 조합 선택 |
| 안전 | 대상 아님·신청 불가 정책이 최대 가능 조합에서 제외되고, 미확인 조건은 금액 아래에 표시됨 |

### 11-2. Definition of Done

- 선정한 정책 3~5개의 공식 출처와 검수자가 기록되어 있다.
- 정책별 정상·탈락·미확인·경계값 테스트가 모두 통과한다.
- 동일 입력으로 새로고침해도 동일 결과가 나온다.
- 결과의 모든 금액을 사람이 다시 계산해 일치함을 확인했다.
- 모바일 화면에서 전체 흐름을 완료할 수 있다.
- 지원금 지급 시점과 계약 시 필요한 목돈을 혼동하지 않게 표시한다.
- 배포 URL에서 발표 시나리오가 동작한다.

## 12. 남은 2주 일정

남은 정규 작업 시간은 **4회 × 4시간 = 16시간**이다. 정책 조사는 세션 밖에서 완료하고, 세션은 구현과 검증에 집중한다.

| 날짜 | 목표 | 세션 중 작업 | 세션 전후 필수 산출물 |
|---|---|---|---|
| **8/12** | 범위와 정책 목록 확정 | 새 흐름·데이터 스키마·화면 골격 | 정책 후보 3~5개 공식 공고 확보, 담당자 배정 |
| **8/17** | 판정과 금액 계산 완성 | 정책 JSON, 자격 규칙, 금액·중복 계산, 단위 테스트 | 정책 데이터 교차 검수 완료 |
| **8/19** | 사용자가 결과까지 도달 | 조건부 질문, 결과 분류, 최종 금액, 신청 링크 | 실제 사용자 입력 시나리오 5건 검수 |
| **8/24** | 배포와 발표 준비 | 모바일 QA, 오류 수정, Vercel 배포, 리허설 | 발표 시나리오와 백업 화면 준비 |
| **8/26** | 발표 | 입력부터 신청 연결까지 시연 | — |

### 12-1. 역할별 핵심 산출물

| 역할 | 핵심 산출물 |
|---|---|
| 기획·리서치 | 정책 3~5개 공식 자료, 구조화 조건, 예외, 중복 관계, 테스트 사례 |
| 개발 | 판정 엔진, 금액·조합 계산, 조건부 질문, 결과 화면, 테스트 |
| 디자인 | 모바일 입력 흐름, 4상태 결과 카드, 금액 요약 |
| 발표·마케팅 | “정책 목록이 아니라 실제 부담을 계산한다”는 서사와 시연 시나리오 |

### 12-2. 일정이 밀릴 때 자르는 순서

| 순서 | 제외 또는 축소 | 유지하는 가치 |
|---|---|---|
| 1 | 결과 공유 이미지·캡처 최적화 | 핵심 계산 유지 |
| 2 | 정책 수를 5개에서 3개로 축소 | 검증 정확도 유지 |
| 3 | 애니메이션·부가 설명 UI | 판정·금액 유지 |
| 4 | localStorage 저장 | 한 세션 내 계산 유지 |
| 자르지 않음 | 조건부 질문, 조건 판정, 중복 제한, 두 금액 요약, 공식 신청 링크 | 제품의 핵심 |

## 14. 발표 서사

> 청년 주거정책은 존재하지만, 조건이 복잡해 내가 받을 수 있는지 알기 어렵습니다.  
> 나이와 소득만 묻고 지원금을 더하면 간단해 보이지만, 기초생활수급 여부·가구 구성·원가구 소득·무주택·중복 수급을 놓쳐 틀린 금액을 만들 수 있습니다.  
> 그래서 우리는 정책을 많이 나열하지 않습니다. 공식 조건을 구조화하고, 입력값을 바탕으로 동시에 성립 가능한 지원 조합을 계산합니다.  
> 사용자는 **최대 지원 가능액**과 이를 반영한 **최종 예상 주거비**를 직관적으로 확인한 뒤, 정책별 남은 조건과 신청 경로를 확인할 수 있습니다.
