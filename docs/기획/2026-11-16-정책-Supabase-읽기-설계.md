# 정책을 Supabase 에서 읽기 — 설계 (A안: 빌드할 때 읽기)

작성: 2026-11-16 · ggue (Claude 정리) · 상태: **DB 적용 · 코드 완료 (브랜치 `feature/policies-from-supabase`) — Vercel 연결 전**
이어지는 작업: 새 정책 알림(웹 푸시) — 이 설계 위에 얹는다. 따로 설계한다.

## 왜 바꾸나

11/11 계획은 "앱은 JSON 을 읽고 Supabase 는 원문·검수 기록 창고"였다(그때 이유: 시연 중 서버가 멈추면 앱도 멈춤,
11/17 멘토 점검까지 시간, 내부 메모 노출 위험). 11/16 팀 결정으로 **Supabase 를 정책의 단일 출처**로 바꾼다.

- 정책을 두 곳(JSON·DB)에 따로 고치던 일을 없앤다 — 지금도 DB 15건 · 앱 15건(현금 8 + 대출·저축 7)의 값이 일부 다르다.
- 새 정책 알림의 "등록"을 **Supabase 에서 정책을 공개 상태로 바꾸는 것** 하나로 만든다.
- 시연은 영상이라(11/08 결정) "무대에서 서버가 멈추는" 위험은 사라졌다.

## 결정: 빌드할 때 읽는다 (A안)

```
팀원이 Supabase 에서 정책 등록·수정 (상태 '운영')
  → Supabase 5분 예약 작업이 공개 데이터 지문이 바뀐 걸 보고 Vercel Deploy Hook (main) 호출 (11/17, 아래 4번)
  → Vercel 빌드: scripts/fetch-app-data.mjs 가 DB 를 읽어 data/*.json 을 다시 쓰고 → next build
  → 최대 5분 + 빌드 1~2분 뒤 정식 앱에 반영
  → (다음 작업) 알림 서버가 매시간 '배포된 앱의 정책 목록'을 보고 새 정책을 알린다
```

B안(화면을 열 때마다 읽기)을 고르지 않은 이유: 정책을 쓰는 화면 12곳이 모두 동기 import 라 로딩·실패 상태를 새로
만들어야 하고, 정책 상세 3종(`find/policies/[id]` · `prepare` · `result/review/[id]`)은 `generateStaticParams` 로
빌드 때 만드는 페이지라 B안이어도 새 정책 상세는 재배포 없이는 안 생긴다.

A안의 덤: DB 표는 익명(anon)에게 **지금처럼 닫아 둔다.** 익명은 공개용 함수 하나만 부를 수 있다(아래 1번).

## 구성

### 1. DB (Supabase) — 칸 추가만, 기존 칸·쿼리는 그대로

11/17 멘토 점검에서 보여 줄 표·`match_policies` 쿼리를 깨지 않도록 **추가만** 한다(새 마이그레이션 파일).

- **공개용 함수 `public.app_policies()`** (11/16 적용, `migrations/20261115172640_app_policies.sql`).
  익명이 부를 수 있는 건 이 함수뿐이고 표는 그대로 닫혀 있다. 빌드는 공개(publishable) 키로 이 함수만 부른다 —
  비밀 키를 Vercel·AWS 에 두지 않는다. 나가는 값은 지금도 앱 번들에 실려 공개된 범위다.
- **공개 기준**: `is_current and status in ('예정', '운영')`. '보류'·'종료'는 앱에 안 나온다.
- Supabase 보안 점검(Advisors)의 경고 2건 — `0028`·`0029` "로그인 없이 부를 수 있는 SECURITY DEFINER 함수" — 은
  **의도한 것**이다. 이 함수가 바로 공개 창구다. 표 권한을 열지 않고 공개 칸만 내보내려고 definer 로 만들었고,
  `search_path` 를 비워 이름 바꿔치기를 막았다(`supabase/tests/app-policies.test.mjs` 가 내부 칸이 안 나가는지 확인).
- 11/16 대조 결과 DB 에 없던 칸 (정책 표에 추가, 전부 비워 둘 수 있음):

  | 칸 | 앱 값 | 이유 |
  |---|---|---|
  | `verified_at` | `verifiedAt` | 팀의 원문 대조일. 확인 기록(policy_checks)에 '일치'가 있으면 그 마지막 날짜가 우선 |
  | `youth_policy_no` · `gov24_service_id` | `youthPolicyNo` · `gov24ServiceId` | 매주 신선도 점검·후보 발굴 스크립트가 쓴다 |
  | `next_round` (jsonb) | `nextRound` | 마감 회차의 다음 일정 `{text, confirmedAt, via}` |
  | `payout_note` | `payoutNote` | 일시금이 '1회 지급'이 아닐 때 한 줄 |
  | `contact_label` · `contact_url` | `contact.department` · `contact.url` | seed 가 문의처를 기관 표로 합치면서 정책별 표시 이름·안내 주소를 잃었다. 비우면 기관 표 값 |

- 규칙 완화 1개: `현금만_지원형태` — '보증료'도 지원 형태(`benefit_type`)를 가질 수 있게. 보증금반환보증 보증료 지원은
  금액 계산(2층)에 들어가는 정책이라 지원 형태가 필요하다. **변환 규칙: `benefit_type` 이 있으면 `policies.json`, 없으면 `loan-products.json`.**
- 앱의 `notes`(내부 검수 메모)는 화면에 쓰이지 않는다 — DB 의 `notes` 가 그 자리이고, 앱 데이터에는 싣지 않는다(`""`).

### 2. DB → 앱 JSON 변환 (`apps/web/scripts/fetch-app-data.mjs` + 변환 모듈)

- `POST {SUPABASE_URL}/rest/v1/rpc/app_policies` 한 번. 키: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`(공개 키).
- `benefit_type` 으로 나눈다: 있으면 `policies.json`(`PolicyMeta`), 없으면 `loan-products.json`(`LoanProductMeta`, 종류는 `kind`).
- `verification.json` 도 같은 실행에서 만든다 — 전에는 SQL 결과를 손으로 붙여 넣었다(`scripts/verification-snapshot.sql`, 이제 안 씀).
- **검사 후 쓰기**: 필수 칸, id 중복, 지역이 `REGION_OPTIONS` 안에 있는지, 날짜 형식. 하나라도 틀리면 빌드를 멈춘다
  → 정식 앱은 직전 배포 그대로 남는다.
- **키가 없으면 건너뛴다**: 로컬 개발·PR 검사·테스트는 저장소에 커밋된 JSON(마지막 스냅숏)을 그대로 쓴다.
  키가 있는데 DB 가 응답하지 않으면 실패(조용히 옛 값으로 배포하지 않는다).
- `package.json` 의 `build` 앞에 붙인다(`prebuild`).

### 3. 전환 안전장치 — 대조 검사

전환 전 **"DB 로 만든 JSON = 지금 커밋된 JSON"** 을 한 칸도 빠짐없이 확인한다. 다르면 두 가지 중 하나다.

- DB 에 칸이 없다 → 1번에서 칸을 추가하고 값을 채운다.
- 값이 다르다(예: 전입 지원 2건, '보류' 상태) → 원문 기준으로 어느 쪽이 맞는지 정하고, 맞는 값으로 DB 를 고친다
  (`edited_by`·`edit_note` 남김). 앱 JSON 은 사람이 11/14 원문 대조한 값이다.

같아진 다음에 Vercel 에 키를 넣는다. 그 순간 화면은 하나도 바뀌지 않아야 한다.

11/16 첫 대조에서 나온 **값** 차이(칸 없음 제외)와 처리:

| 정책 | 차이 | 처리 |
|---|---|---|
| 익산형 청년월세 요약 | 앱 "선착순 250명 한정" · DB "2026년 신규 230여 명 (선착순 아님)" (DB v2, 11/13 통화 반영) | DB 값을 쓴다 — 화면 문구가 바뀌는 유일한 곳 |
| 전입장려금 · 주소전입 학생 지원 | DB 는 11/12 보조금24 초안('보류'), 앱은 11/14 조례 원문 검수값(11/15 반영) | 11/15 문서 '남은 것' 1번대로 DB 를 앱 값으로 맞추고 '운영'으로. 버전이 올라가 재검수 필요 |
| 대출 4건 문의처 주소·이름 | seed 가 같은 부서를 한 행으로 합치며 정책별 주소·꼬리말을 잃음 | `contact_label` · `contact_url` 에 앱 값 |
| 익산 대출 2건 전화 확인일 | 앱 없음 · DB 11/03 (같은 번호를 11/03 에 확인한 기록) | DB 값을 쓴다 — 같은 번호라 사실이다 |
| 확인일(`verifiedAt`) | 확인 기록이 있는 정책은 그 날짜(예: 국토부 청년월세 11/14)가 11/03 대신 나온다 | 더 최근의 실제 확인이라 그대로 둔다 |

### 4. 자동 재배포 (11/17 — `supabase/migrations/20261117104553_app_rebuild.sql`)

- Vercel: main 용 Deploy Hook(이름 `supabase`)을 만들고, 그 주소를 Supabase Vault 에 `vercel_deploy_hook` 로 넣는다(저장소 · 채팅에 적지 않는다).
- Supabase: Database Webhook(표 변경마다 호출) 대신 **5분마다 `public.app_policies()` 결과의 md5 를 보고, 지난번 호출 때와 다르면 Hook 을 한 번 부른다**(`pg_cron` + `pg_net`).
  - 앱에 나가는 것만 본다 — 고친 이유만 바꾸거나 '보류' 정책을 고치면 빌드하지 않는다. 검수 기록(배지)은 함수 결과에 들어 있어 바뀌면 빌드한다
  - 여러 번 고쳐도 5분 단위로 한 번. 호출이 실패하면(2xx 아님 · 시간 초과) 다음 5분에 다시
  - 상태: `select * from private.app_rebuild_state;` · 손으로 한 번: `select private.request_app_rebuild();`

### 5. 2층 규칙이 없는 정책

2층 판정(무주택·가구소득 등)은 정책마다 `lib/policy-rules.ts` 에 코드로 있다. DB 에만 등록한 새 정책은 규칙이 없어서
지금 `lib/eligibility.ts` 가 **확인 항목 0개 → '예상적용'** 으로 판정한다(거짓 통과). 규칙이 없으면
"세부 조건은 공고 원문에서 확인" 한 항목을 `unknown` 으로 넣어 **'조건충족시가능'** 이 되게 고친다.
1층(찾기·목록·상세)과 알림은 DB 칸만으로 돌아간다.

## 테스트

- 변환 모듈: DB 행 → 앱 JSON 단위 테스트(픽스처), 검사 실패 경우들.
- 대조 검사: 실제 DB 를 읽어 커밋된 JSON 과 비교하는 스크립트(`--check`) — 키가 있을 때만.
- eligibility: 규칙 없는 정책이 '조건충족시가능' 이 되는지.
- 기존 tsc · vitest · next build · Supabase 검사 그대로 통과.

## 바뀌는 팀 규칙 (전환 후 문서에 반영)

- 11/11 계획 '절대 하지 말 것' 2·3번 폐기: 앱(빌드)이 Supabase 를 읽고, DB 값이 JSON 이 된다.
- 정책 값은 **DB 에서만 고친다.** `apps/web/data/policies.json`·`loan-products.json`·`verification.json` 은 생성물(스냅숏).
- `CLAUDE.md` "정책 1건 추가할 때 손대는 곳" 을 DB 기준으로 고친다.

## 하지 않는 것

- 화면에서 DB 직접 읽기(B안), 익명 읽기 열기.
- 상담 창구(`consult-centers.json`)·소득 기준표 이전 — 이번 범위 밖.
- 마감 임박·신청 시작 알림 — 정책 8건 중 4건 마감·4건 상시라 지금은 보낼 대상이 없다.
