# 카카오 로그인 설계 — 기기를 바꿔도 이어 보기

작성일 2026-11-04 · 대상 `apps/web`(정적 사이트) + 신규 `infra/`(AWS CDK) + 신규 `apps/api`(Lambda)

## 왜

로그인한 이용자의 답을 서버에 저장해 **기기를 바꿔도 불러올 수 있게** 한다.

지금은 PRD F0-13·F2-10("답변은 브라우저에만 저장하고 서버로 전송하지 않는다")과 548행("개인정보와 소득
정보는 브라우저 밖으로 나가지 않는다")에 따라 모든 답이 localStorage 에만 있다. 이 설계는 그 원칙을
**"로그인 전에는 브라우저에만, 동의한 로그인 이용자는 서울 리전 서버에 저장"**으로 바꾼다.

## 결정 사항

| 질문 | 결정 | 이유 |
|---|---|---|
| 클라우드 | **AWS 서울 리전(`ap-northeast-2`)** | 데이터는 국내 데이터센터. 자료가 많고 관리형 서비스로 운영 부담이 적다. 운영사는 미국 기업 — 개인정보 처리방침에 처리 위탁으로 적는다 |
| 구성 | **서버리스**: Cognito + API Gateway(HTTP API) + Lambda + DynamoDB | 상시 서버가 없어 OS 보안 업데이트·백업 운영이 없다. 시연 규모에서 비용이 거의 0 |
| 로그인 | **카카오 하나로 시작** (Cognito 에 OIDC 로 연결) | 국내 청년 대부분이 계정을 갖고 있다. 비밀번호를 우리가 저장하지 않는다 |
| 필수 여부 | **선택 로그인** | 로그인 없이 지금처럼 전부 쓸 수 있다. 로그인 전에는 서버로 아무것도 보내지 않는다 |
| 가입 유도 | `/find/result` "지원금 N건 자세히 보기" 에서 **닫을 수 있는 시트** | 결과를 막지 않는다(멘토링 목표인 "데이터를 보여주기"와 충돌하지 않게) |
| 저장 범위 | **전부**: 1층 답, 2층 계약 조건, 2층 자격 답, 신청 체크리스트 | 기기 간 이어 보기가 목적. 대신 아래 보호 장치를 필수로 둔다 |

검토하고 택하지 않은 것:

- **네이버클라우드** — 국내 기업·국내 서버로 설명이 가장 깔끔하고 Micro Server 1년 무료지만, 서버를
  직접 운영해야 하고 자료가 적다
- **EC2 + PostgreSQL + 직접 만든 로그인** — 서버 보안 업데이트·백업을 팀이 감당해야 한다. 민감 정보를
  저장하기로 한 만큼 운영 실수가 더 큰 위험이다
- **Amplify Gen 2** — 시작은 빠르지만 AWS 전용 방식에 깊게 묶이고 내부를 팀이 이해하기 어렵다
- **필수 로그인 / 결과를 막는 가입 벽** — 처음 온 사람이 혜택을 확인하기 전에 떠난다

## 카카오 ↔ Cognito 연결 시험 결과 (2026-11-04)

설계의 가장 큰 불확실성이었다. 시험용 자원(`perky-spike`)을 서울 리전에 만들어 끝까지 확인했다.

- 흐름: 브라우저 → Cognito Hosted UI(`identity_provider=Kakao`) → 카카오 로그인 → Cognito
  `/oauth2/idpresponse` → 앱 `/auth/callback` → PKCE 로 코드 교환 — **성공**
- 카카오 OIDC 설정(`https://kauth.kakao.com/.well-known/openid-configuration`):
  issuer `https://kauth.kakao.com`, authorize `https://kauth.kakao.com/oauth/authorize`,
  token `https://kauth.kakao.com/oauth/token`, userinfo `https://kapi.kakao.com/v1/oidc/userinfo`,
  jwks `https://kauth.kakao.com/.well-known/jwks.json`. 토큰 엔드포인트 인증은 **`client_secret_post` 만**
  지원 — Cognito 와 문제없이 맞았다
- Cognito IdP 설정: `attributes_request_method=GET`, `authorize_scopes=openid`, 속성 매핑 `username=sub`
- ID 토큰: 발급자 `cognito-idp.ap-northeast-2`, `identities[0].providerName=Kakao`, `sub` 는 36자 UUID,
  **이름·이메일·프로필 없음**(카카오 동의항목을 전부 끔), refresh token 발급
- 카카오 새 콘솔에서 **Redirect URI 는 [앱] > [플랫폼 키] > REST API 키** 에 등록한다
  (카카오 로그인 메뉴가 아님 — KOE006 로 확인)
- **Cognito 안에는 카카오 회원 식별번호가 사용자 이름(`kakao_…`)으로 남는다.** 연동 로그인에서 피할 수
  없다. 사용자 데이터 DB 에는 Cognito `sub` 만 저장한다 — 동의 화면·처리방침에도 이대로 적는다

## 구조

```
[브라우저 · Vercel 정적 사이트 https://wonvengers.vercel.app]
   │ ① "카카오로 계속하기"  (oidc-client-ts, Authorization Code + PKCE)
   ▼
[Cognito Hosted UI · 서울] ──② OIDC──▶ [카카오]
   │ ③ 토큰 발급 → /auth/callback
   ▼
[브라우저] ──④ GET/PUT/DELETE + Bearer 토큰──▶ [API Gateway HTTP API: JWT authorizer]
                                                        │
                                                 [Lambda (Node 22): 저장·불러오기·삭제]
                                                        │
                                                 [DynamoDB: 사용자당 1항목]
```

- 리전: 전부 `ap-northeast-2`. CDK 스택에 리전을 고정해 다른 리전에 만들어지지 않게 한다
- 프론트: `output: "export"` 정적 빌드를 유지한다. 서버 코드 없음
- 저장소 구성: `infra/`(CDK TypeScript), `apps/api/`(Lambda 핸들러 — 핵심 로직은 순수 함수로 두고 Vitest)
- 콜백·로그아웃 URL: `https://wonvengers.vercel.app/auth/callback`, `http://localhost:3000/auth/callback`
  (로그아웃은 각 `/`). Vercel 미리보기 주소는 허용하지 않는다

## API

모든 경로에 JWT authorizer(발급자·audience 검증). 사용자 ID 는 **토큰의 `sub` 에서만** 꺼낸다 —
요청 본문·경로·쿼리의 사용자 ID 는 받지 않는다.

| 경로 | 동작 | 응답 |
|---|---|---|
| `GET /me/data` | 내 항목 읽기 | 200 `{ data, updatedAt }` / 항목 없으면 204 |
| `PUT /me/data` | 내 항목 통째로 저장(형식 검사 후) | 200 `{ updatedAt }` / 400 형식 오류 / 413 크기 초과 |
| `DELETE /me` | **회원 탈퇴**: 카카오 연결 끊기 → 내 항목 삭제 → Cognito 사용자 삭제 | 204 |

- 요청 본문 최대 64KB
- "처음부터 다시"는 별도 경로가 없다 — 비운 데이터를 `PUT` 한다(아래 "처음부터 다시")
- 탈퇴 순서: 카카오 연결 끊기가 실패하면 멈추고 500 — DB·Cognito 를 먼저 지우면 다시 시도할 근거(카카오
  식별번호)가 사라진다. 카카오에서 이미 끊긴 사용자(오류 코드 "이미 연결 해제")는 성공으로 본다
- `PUT` 은 낙관적 동시성: 요청에 `baseUpdatedAt` 을 담고, 서버 값과 다르면 409 — 프론트가 충돌 질문을 띄운다

## 데이터

DynamoDB 테이블 `perky-user-data`, 파티션 키 `userId` 하나.

```
userId          : Cognito sub (UUID)
schemaVersion   : 1
answers         : 1층 답(DiscoveryAnswers) + answeredKeys
listing         : 2층 계약 조건(ListingInput) | null
profile         : 2층 자격 답(EligibilityProfile) + eligibilityAnsweredKeys | null
declared        : perky.declared 값 | null
checklists      : { [policyId]: 체크 상태 }
consentVersion  : "2026-11-04"
consentAt       : ISO 시각
updatedAt       : ISO 시각
expiresAt       : 마지막 저장 + 365일 (epoch 초, DynamoDB TTL)
```

- 지금 localStorage 키(`perky.answers`, `perky.answered`, `housing-benefit:listing`,
  `housing-benefit:profile`, `perky.eligibility-answered`, `perky.declared`,
  `perky.application-checklist:*`)를 그대로 옮긴 구조다
- 형식 검사는 기존 타입(`lib/types.ts`)과 같은 규칙을 Lambda 에서 다시 한다(신뢰 경계)
- 테이블: 저장 시 암호화(기본), PITR(실수 복구), TTL(1년 미접속 자동 삭제)

## 동기화 규칙 (`lib/storage.ts` 뒤에 둔다)

- **로그인 전**: 지금과 같다. 서버 호출 0번
- **처음 로그인 직후**: 동의 화면 → 동의하면
  - 서버 항목 없음 → 이 기기 답을 올린다
  - 서버 항목 있고 이 기기에도 답 있음 → "이 기기의 답 / 저장된 답 중 무엇을 쓸까요?"
  - 서버 항목만 있음 → 내려받아 localStorage 를 채운다
- **로그인 후**: 서버가 기준. localStorage 는 화면을 빨리 그리기 위한 사본이다. 쓰기는 1.5초 모아서 `PUT`
- **오프라인·실패**: 사본에 남기고 상단바에 "저장 안 됨 · 다시 시도". 다음 성공 때 함께 올린다
- **로그아웃**: 이 기기의 사본을 지운다(공용 PC 에 개인정보를 남기지 않음)
- 토큰 보관: access/id 토큰은 메모리, refresh token 은 localStorage(`perky.auth`) — 정적 사이트라 HttpOnly
  쿠키를 쓸 수 없다. XSS 위험을 줄이려고 CSP 를 강화한다(아래 보안)

## 화면

1. **가입 제안 시트** — `/find/result` "지원금 N건 자세히 보기"를 처음 누를 때
   - "이 결과를 저장해 둘까요? 카카오로 3초 만에 저장하고, 다른 기기에서도 이어 보세요."
   - [카카오로 계속하기](카카오 공식 노란 버튼 가이드) / [로그인 없이 보기](텍스트 버튼 → 바로 목록)
   - 닫으면 그 기기에서는 다시 띄우지 않는다(`perky.signup-dismissed`). 로그인 상태면 띄우지 않는다
   - 포커스 트랩, Esc 로 닫기, 닫으면 원래 버튼으로 포커스 복귀
2. **`/auth/callback`** — 코드 교환 후 처음이면 `/auth/consent`, 아니면 로그인 전 화면으로
3. **`/auth/consent`** — 저장 항목 표(민감 항목 명시: 소득·재산·수급 여부), 목적(기기 간 이어 보기),
   보관 기간(마지막 저장 후 1년), 저장 위치(AWS 서울 리전), 카카오 식별번호는 로그인 서비스에만 있다는 점,
   삭제 방법. [동의하고 저장] / [동의하지 않음 → 즉시 로그아웃]. **동의 전에는 서버로 아무것도 보내지 않는다**
4. **상단바** — `TopBar` 의 오른쪽 자리(`right`). 로그인 전 비움, 로그인 후 사람 아이콘(→ `/account`),
   저장 실패 시 작은 경고
5. **`/account`** — 로그인 상태, 마지막 저장 시각, [로그아웃], [회원 탈퇴], 처리방침 링크
   - 회원 탈퇴 확인: "저장된 답과 회원 정보가 모두 지워지고 되돌릴 수 없어요." [탈퇴하기] / [취소]
   - 끝나면 이 기기 사본을 지우고 로그아웃 → "탈퇴가 끝났어요" 안내. 다시 카카오로 로그인하면 새 회원
7. **"처음부터 다시"** — 따로 화면에 들어가지 않고 답을 고르는 흐름 안에서
   - 위치: `/find/result`·`/find/policies` 의 "조건 수정" 옆 텍스트 버튼, `/find` 상단 답 요약 줄 끝
     (답이 하나 이상 있을 때만)
   - 확인 시트: "고른 답을 모두 지우고 첫 질문부터 다시 할까요?" [다시 하기] / [취소]
   - 지우는 것: 1층 답, 2층 계약 조건·자격 답, **신청 체크리스트**(첫 항목이 "자격 조건 확인"이라 답이
     바뀌면 예전 체크가 맞지 않는다), `perky.declared`. 남기는 것: 로그인 상태, 가입 시트 닫음 기록
   - 지운 뒤 `/find?q=birth` 로 `replace`(지운 화면으로 뒤로가기 되돌아가지 않게)
   - 로그인 전·후 똑같이 동작한다. 로그인 상태면 비운 데이터를 즉시 `PUT` — 다른 기기에서도 빈 상태
   - 계정 화면에는 "저장된 답 지우기"를 따로 두지 않는다
6. **`/privacy`** — 수집 항목·목적·보관 기간·처리 위탁(AWS)·파기 절차·문의처. **정식 공개 전 팀·학교 검토**

## 보안 (필수)

- 사용자 ID 는 토큰 `sub` 에서만. **"다른 사용자 토큰으로 남의 데이터를 읽거나 지울 수 없다"를 자동 테스트**
- JWT authorizer 를 모든 경로에. 발급자·audience(app client id) 검증
- Lambda 역할은 그 테이블의 `GetItem`/`PutItem`/`DeleteItem` + Cognito `AdminGetUser`·`AdminDeleteUser`(그 풀만)
  + SSM `/perky/kakao/admin-key` 읽기
- 카카오 연결 끊기: 서버에서 카카오 **Admin 키**로 `POST https://kapi.kakao.com/v1/user/unlink`
  (`target_id_type=user_id`, `target_id`=Cognito 사용자의 카카오 식별번호). 앱은 Cognito 를 거쳐 로그인해서
  카카오 사용자 토큰을 갖고 있지 않으므로 Admin 키 방식이다. Admin 키는 모든 사용자에 대한 권한이라
  Lambda 안에서만 쓰고 SSM SecureString 으로만 보관한다. 카카오 정책상 탈퇴 시 연결 끊기 의무 여부는
  구현 전에 카카오 문서로 다시 확인한다
- CORS: `https://wonvengers.vercel.app`, `http://localhost:3000` 만
- 본문 64KB 제한, 저장 전 형식 검사, 알 수 없는 키 거부
- 로그에 사용자 데이터 값을 남기지 않는다(구조화 로그에 `userId` 해시와 결과 코드만)
- 카카오 client secret·Admin 키는 SSM Parameter Store(`/perky/kakao/client-secret`, `/perky/kakao/admin-key`,
  SecureString). 저장소에 커밋 금지
- CSP: `connect-src` 를 Cognito 도메인·API 도메인으로 제한, 인라인 스크립트 최소화
- 계정: 루트 MFA·제로 지출 예산 완료(2026-11-03), 작업은 IAM 사용자 `perky-dev`(MFA)
- **AWS Organizations·IAM Identity Center 를 켜지 않는다** — 무료 플랜이 자동으로 유료 전환된다

- 배포: `cdk deploy --profile perky`. 프론트 환경변수(`NEXT_PUBLIC_COGNITO_DOMAIN`, `NEXT_PUBLIC_COGNITO_CLIENT_ID`,
  `NEXT_PUBLIC_API_URL`)는 Vercel 프로젝트 설정에 넣는다

## 작업 순서

브랜치 `feature/kakao-login` (develop 기준)

1. **인프라** — `infra/` CDK: User Pool(Lite) + 도메인 + 카카오 OIDC IdP + 앱 클라이언트, DynamoDB(PITR·TTL),
   HTTP API + JWT authorizer, Lambda + 최소 권한, CORS, 예산 알림. `cdk synth` 스냅샷 테스트
2. **API** — `apps/api`: 핸들러 3개, 형식 검사, 크기 제한, 낙관적 동시성, 남의 데이터 차단 테스트
3. **인증 클라이언트** — `lib/auth.ts`(oidc-client-ts 래핑): 로그인·콜백·토큰 갱신·로그아웃
4. **저장 계층** — `lib/storage.ts` 뒤에 원격 동기화. 기존 화면 코드는 그대로 두고 저장 함수만 갈아낀다
5. **화면** — 가입 시트, `/auth/callback`, `/auth/consent`, 상단바, `/account`, `/privacy`
6. **문서** — PRD F0-13·F2-10·548행 개정, 처리방침 초안, 배포 체크리스트
7. **검증** — 아래 테스트 + 실제 카카오 계정으로 두 브라우저 간 이어 보기, 시험용 자원 정리

## 테스트

- **API**: 형식 검사, 64KB 초과 413, 409 충돌, **다른 `sub` 토큰으로 남의 항목 접근 불가**, 탈퇴 순서
  (카카오 끊기 실패 시 DB·Cognito 그대로, "이미 연결 해제"는 성공)
- **저장 계층**: 로그인 전 서버 호출 0번, 동의 전 서버 호출 0번, 충돌 시 고른 쪽 유지, 로그아웃 시 사본 삭제,
  오프라인 후 재시도
- **화면**: 시트 표시·닫기·다시 안 뜸·로그인 상태면 안 뜸, 동의 거부 시 로그아웃, 탈퇴 확인,
  "처음부터 다시" — 확인 후 1·2층 답과 체크리스트가 비고 `?q=birth` 로 replace, 로그인 상태면 빈 데이터 `PUT`
- **인프라**: `cdk synth` 스냅샷 — 리전 고정, CORS 출처, Lambda 권한 범위, PITR·TTL
- **기존**: vitest 전체, `scripts/check-back-nav.mjs` 6개 시나리오 그대로 통과
- **실제 환경**: 기기 A 저장 → 기기 B 로그인 후 불러오기, "처음부터 다시" 후 기기 B 도 빈 상태,
  탈퇴 후 카카오 "연결된 서비스"에서 Perky 가 사라지고 재로그인 시 새 회원·동의 화면
