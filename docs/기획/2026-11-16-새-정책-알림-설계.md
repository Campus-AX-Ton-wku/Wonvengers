## 구조 — 지금 AWS 스택(PerkyStack)에 붙인다

사용자 답(DynamoDB `perky-user-data`)과 로그인(Cognito)이 이미 AWS 서울에 있다. 같은 곳에서 판정하고 보낸다.
(Supabase Edge Function 은 답을 AWS 에서 끌어와야 하고, Vercel Cron 은 정적 사이트라 서버를 따로 세워야 해서 고르지 않았다.)

```
Supabase '운영' ─(webhook)→ Vercel 재배포 ─→ 앱 /policies.json (빌드 때 생성)
                                                   │
EventBridge 매시 정각 09~21시 KST ─→ 알림 Lambda ──┤ ① /policies.json 읽기
                                                   │ ② perky-push 의 '이미 알린 정책'과 비교 → 새 정책
                                                   │ ③ 구독한 사용자마다 perky-user-data 의 답으로 1층 판정(apps/web/lib/filter.ts)
                                                   │ ④ 웹 푸시 (VAPID, 한 사람 한 통)
                                                   └ ⑤ '이미 알린 정책'에 추가
```

알림 서버는 DB 가 아니라 **배포된 앱의 목록**을 본다. DB 값이 검사에 걸려 빌드가 멈추면 앱에는 정책이 없는데
알림만 가는 일이 생기기 때문이다. 판정은 앱과 **같은 코드**(`tagPolicy`)를 묶어 써서 화면과 어긋나지 않는다
(API Lambda 가 `apps/web/lib/user-data.ts` 를 묶는 것과 같은 방식).

## 1. 앱 (apps/web)

### `/policies.json` (새 경로, 정적)
`app/policies.json/route.ts` — `dynamic = "force-static"`, `GET` 이 `data/policies.json` 을 그대로 돌려준다.
정적 export 라 빌드 때 파일로 굽힌다. 이미 화면 번들에 실린 값이라 새로 공개되는 것은 없다.

### 서비스 워커 `public/sw.js`
- `push`: 받은 JSON `{title, body, url, tag}` 로 `showNotification`(아이콘 `/icon-192.png`). iOS 는 푸시마다 알림을 띄워야 권한이 유지된다.
- `notificationclick`: 알림을 닫고, 열린 Perky 창이 있으면 그 창을 `url` 로 옮겨 포커스, 없으면 새 창.
- **캐시·fetch 가로채기는 하지 않는다**(오프라인 PWA 는 범위 밖 — 캐시가 옛 화면을 보여 주는 사고를 피한다).
- 등록은 내 계정 화면에서만 한다. 한 번 등록된 워커는 앱을 닫아도 푸시를 받는다.

### `lib/push.ts`
- `pushSupport()`: `'unsupported' | 'needs-home-screen' | 'ready'` — iOS 이면서 standalone 이 아니면 `needs-home-screen`.
- `pushState()`: 권한(`Notification.permission`) + 지금 구독 여부.
- `enablePush()`: (버튼 클릭 안에서) 워커 등록 → 권한 요청 → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey })` → `PUT /me/push`.
- `disablePush()`: 구독 찾기 → `unsubscribe()` 먼저 → `DELETE /me/push`. 기기 구독을 먼저 끊어, 서버 호출이 늦거나 실패해도(로그아웃이 떠나도) 이 기기에는 더 오지 않는다. `enablePush` 는 켠 계정(sub)을 `perky.push-owner` 에 적는다.
- 계정 화면을 열 때 이미 구독 중이면 `PUT /me/push` 로 한 번 갱신한다(서버 TTL 연장 · 구독 주소가 바뀐 경우 대비).
- 공개 키: `NEXT_PUBLIC_VAPID_PUBLIC_KEY`. 없으면 알림 칸을 그리지 않는다(로그인이 없는 빌드와 같은 방식).

### 내 계정 화면 — 알림 칸

| 상태 | 보이는 것 |
|---|---|
| 꺼짐 | **[알림 켜기]** · "새 지원금이 올라오면 내 조건에 맞는지 보고 알려 드려요 (낮 9시~밤 9시)" |
| 켜짐 | "알림 켜짐" · [알림 끄기] |
| 사파리 탭(iOS, 홈 화면 아님) | "홈 화면에 추가한 Perky에서 알림을 켤 수 있어요" |
| 지원 안 함 | "이 브라우저는 알림을 지원하지 않아요" |
| 권한 거부 | "알림이 꺼져 있어요. 기기 설정에서 Perky 알림을 허용해 주세요" |
| 답 저장 동의 없음 | [알림 켜기] 대신 "답을 저장해야 맞춤 알림을 받을 수 있어요" |

### 로그아웃 · 탈퇴
- 로그아웃: `signOut` 전에 `disablePush()` (최대 3초 기다림). 공용 기기에 다른 사람의 맞춤 알림이 오지 않게. 계정 화면은 켜짐으로 보이기 전에 소유자(`perky.push-owner`)가 지금 로그인한 계정인지 확인하고, 다르면 기기 구독만 끊고 꺼짐으로 보여 준다.
- 탈퇴: 서버 `DELETE /me` 가 그 사용자의 구독을 모두 지운다(아래). 기기 구독도 끊는다.

### 개인정보 처리방침 (`/privacy`)
"알림을 켜면 이 기기의 알림 구독 정보(푸시 서비스 주소·암호 키)를 저장하고, 알림을 끄거나 로그아웃·탈퇴하면 지운다.
알림 문구에는 정책 이름만 들어가고 소득 등 답은 넣지 않는다" 를 더한다. 동의 버전은 올리지 않는다 —
[알림 켜기]와 기기 권한 허용이 그 동의다.

## 2. 서버 (apps/api · infra)

### DynamoDB `perky-push` (새 표)

| 키 | 값 |
|---|---|
| `userId` (파티션) | Cognito sub. 상태 항목은 `__state__` |
| `deviceId` (정렬) | 구독 주소의 SHA-256 앞 32자. 상태 항목은 `announced` |
| 구독 항목 | `endpoint` · `p256dh` · `auth` · `createdAt` · `updatedAt` · `expiresAt`(TTL, 마지막 갱신 + 1년) |
| 상태 항목 | `policyIds`(이미 알린 정책 id 집합) · `updatedAt` |

한 사용자 기기 5대까지 — 넘으면 가장 오래된 구독을 지운다.

### API (기존 HTTP API · JWT · 같은 Lambda)

| 경로 | 본문 | 결과 |
|---|---|---|
| `PUT /me/push` | `{ endpoint, keys: { p256dh, auth } }` — https 주소 1000자 이하, 키는 base64url | 204 |
| `DELETE /me/push` | `{ endpoint }` | 204 (없어도 204) |
| `DELETE /me` (기존) | — | 카카오 끊기 → 답 삭제 → **구독 모두 삭제** → Cognito 삭제 |

사용자는 토큰의 sub 로만 정한다(기존 규칙). 알 수 없는 키는 거부. 로그에는 해시한 사용자 id 만.

### 알림 Lambda (`apps/api/src/notifier/`)

1. 상태 항목을 읽는다. **없으면 첫 실행** — 지금 `/policies.json` 의 id 를 모두 '이미 알림'으로 적고 보내지 않고 끝.
2. `/policies.json` 을 읽는다(10초). 실패하면 기록만 하고 끝 — 다음 정시에 다시.
3. 새 정책 = 이미 알린 목록에 없는 id. 그중 **이미 마감된 것**(`applicationEnd` < 오늘)은 알리지 않고 목록에만 넣는다.
4. 새 정책이 없으면 끝.
5. 구독 항목을 모두 읽어 사용자별로 묶는다(Scan — 사용자가 적다).
6. 사용자마다 `perky-user-data` 에서 답을 읽는다. 없거나 동의 버전이 없으면 건너뜀. `resolveAnswers(오늘)` →
   지역이 없으면 건너뜀 → 새 정책마다 `tagPolicy` → '가능성 있음' · '확인 필요'만 남긴다 → 0건이면 건너뜀.
7. 문구를 만들어 그 사용자의 기기마다 보낸다(`web-push`, TTL 12시간). 404 · 410 이면 그 구독을 지운다.
8. 새 정책 id 를 '이미 알림'에 더한다. — 보낸 **뒤에** 적으므로, 그 사이에 멈추면 드물게 두 번 갈 수 있다(빠지는 것보다 낫다).
9. 기록: 새 정책 수, 받은 사람 수, 보낸 기기 수, 지운 구독 수. 사용자 id 는 남기지 않는다.

- 시간: EventBridge 규칙 `cron(0 0-12 * * ? *)` (UTC 0~12시 = 서울 9~21시). 코드도 서울 9~21시 밖이면 보내지 않는다 —
  손으로 실행할 때 `{"force": true}` 를 주면 예외.
- 키: VAPID 비밀 키는 SSM SecureString `/perky/push/vapid-private-key`(CLI 로 넣는다 — CDK 는 SecureString 을 못 만든다),
  공개 키는 Lambda 환경변수와 Vercel `NEXT_PUBLIC_VAPID_PUBLIC_KEY`. subject 는 `https://wonvengers.vercel.app`.
- 권한(최소): `perky-push` Scan · Put · Delete · Get, `perky-user-data` GetItem, 그 SSM 파라미터 하나.
- 스택 출력에 `NotifierFunctionName` 을 더한다(시연 때 손으로 실행).

### 문구 (잠금 화면에 보이므로 소득·나이 같은 답은 넣지 않는다)

| 경우 | 제목 | 본문 | 누르면 |
|---|---|---|---|
| 1건 · 가능성 있음 | 새 지원금이 올라왔어요 | {정책명} — 조건에 맞을 가능성이 있어요 | `/find/policies/{id}` |
| 1건 · 확인 필요 | 새 지원금이 올라왔어요 | {정책명} — 받을 수도 있는 지원금이에요. 조건을 확인해 보세요 | `/find/policies/{id}` |
| 여러 건 | 새 지원금 N건이 올라왔어요 | {첫 정책명} 외 N-1건 — 받을 수 있을지 확인해 보세요 | `/find/policies` |

여러 건일 때 첫 정책은 '가능성 있음'을 먼저, 그다음 DB 순서.

## 자동 배포 (11/16 추가)

웹은 Vercel 이 main 에서 자동 배포하지만 AWS(PerkyStack)는 손으로 `cdk deploy` 해 왔다. 알림 서버를 고칠 때마다
손으로 배포하면 빠뜨리므로 GitHub Actions 로 자동화한다(`.github/workflows/deploy-aws.yml`).

- **접근 키를 저장하지 않는다.** GitHub OIDC 로 역할 `perky-github-deploy` 를 빌린다. 신뢰 조건은
  `repo:Campus-AX-Ton-wku/Wonvengers:environment:aws-production` 하나 — 배포 환경 `aws-production` 에서 돈 작업만.
- `aws-production` 은 **ggue 승인 + main 브랜치만**. 승인 전에는 아무것도 바뀌지 않는다.
- 역할이 할 수 있는 일은 cdk bootstrap 이 만든 `cdk-hnb659fds-*` 역할 빌리기 하나(실제 변경은 CloudFormation).
- 언제: main 에 `infra/` · `apps/api/` · API 가 묶는 웹 파일 7개가 바뀌면. 배포 전에 api · infra 검사와 `cdk diff`.
- 처음 한 번은 손으로 배포해야 역할이 생긴다(이번 알림 배포에 함께). 비밀값(카카오 · VAPID)은 SSM, 예산 메일은 지난 배포 값.
- PR 검사에 api · infra 검사와 `cdk synth`(묶기)를 더해, main 에 가기 전에 깨진 배포를 잡는다.

## 3. 시연 절차 (영상)

1. 팀: 원문 검수를 마친 익산 정책 1건을 DB 에 `status = '보류'` 로 넣어 둔다(앱에 안 나옴). 2층 규칙은 없어도 된다.
2. 아이폰 홈 화면 Perky → 로그인 → 내 계정 → [알림 켜기] → 허용.
3. Supabase 에서 그 정책을 '운영'으로 → 자동 재배포(1~2분) → `/policies.json` 에 실렸는지 확인.
4. 알림 Lambda 를 손으로 한 번 실행 — 함수 이름은 스택 출력 `NotifierFunctionName`:
   `aws lambda invoke --function-name "$(aws cloudformation describe-stacks --stack-name PerkyStack --query "Stacks[0].Outputs[?OutputKey=='NotifierFunctionName'].OutputValue" --output text --profile perky)" --cli-binary-format raw-in-base64-out --payload '{"force":true}' --profile perky out.json`
5. 잠금 화면에 알림 → 누르면 그 정책 상세.

## 4. 테스트

- 알림 판단(순수 함수): 새 정책 고르기(첫 실행 · 마감 · 이미 알림), 받는 사람(지역 없음 · 동의 없음 · 해당 없음), 문구 3종, 시간 창.
- 발송: web-push 를 가짜로 바꿔 404 · 410 → 구독 삭제, 그 외 오류는 다음 기기로 계속.
- API: `PUT/DELETE /me/push` 형식 검사 · 5대 제한 · sub 로만, `DELETE /me` 가 구독까지 지움 (기존 `apps/api/test` 방식).
- 스택: 표 · 규칙 · 권한 · 경로 (기존 `infra/test` 스냅숏).
- 화면: 알림 칸의 상태 6가지, 로그아웃이 구독을 끊는지(jsdom, pushManager 가짜).
- 실제: 아이폰 홈 화면 앱에서 3절 순서대로.

## 하지 않는 것

- 마감 임박 · 신청 시작 알림, 정책 상세의 [이미 신청했어요] — 정책 데이터에 다음 회차가 채워지면 다시 본다.
- 오프라인 캐시(서비스 워커 fetch), 앱 홈 화면 개편, 안드로이드 전용 처리, 카카오 알림톡.
- 사용자별 알림 시간 설정.
