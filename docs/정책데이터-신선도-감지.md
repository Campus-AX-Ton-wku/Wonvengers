# 정책 데이터 신선도 감지

`policies.json` 은 팀이 공고 원문을 읽고 손으로 채운 데이터다. 이 문서는
**그 데이터가 낡는 것을 자동으로 알아채되, 자동으로 고치지는 않는** 장치를 설명한다.

- 스크립트: `apps/web/scripts/check-policy-freshness.mjs` (`npm run check:freshness`)
- 자동 실행: `.github/workflows/policy-freshness.yml` — 매주 월요일 09:00 KST
- 결과: 검토할 것이 있으면 `정책데이터` 라벨이 붙은 이슈가 열린다

## 왜 자동으로 고치지 않는가

2026-08-30 에 두 API 를 실제로 조회해 확인한 사실이다.

| 확인한 것 | 그래서 |
|---|---|
| 판정에 쓰는 값(`monthlyCap`·`maxMonths`·`requiredInputs`·소득기준)이 **어느 API 에도 없다** | 애초에 자동 갱신 대상이 아니다. 공고 원문을 읽어야만 나오는 값이다 |
| 보조금24 는 전국 청년월세 신청기한을 **"2026년 상반기"** 라 적고 있다. 실제 접수는 3/30~5/29 로 이미 끝났고 앱이 맞게 갖고 있다 | 무인 반영은 **맞는 값을 틀린 값으로 덮어쓴다** |
| `verifiedAt` 은 "팀이 공고 원문과 대조한 날짜"라는 뜻이다 | 기계가 값을 바꾸면 이 날짜가 거짓말이 된다 |

접수가 끝난 정책을 걸러내는 일은 이미 데이터 갱신 없이 되고 있다 —
`isWithinWindow(오늘, start, end)` 가 렌더할 때마다 계산한다
(`lib/eligibility.ts`, `lib/discovery.ts`, `app/find/PolicyCard.tsx`).
자동화가 실제로 필요한 지점은 **새 회차가 열렸는데 앱이 모르는 경우**다.

## 두 소스를 함께 쓰는 이유

어느 쪽도 혼자서는 부족하고, 약점이 서로 반대다.

| | 보조금24 (행안부) | 온통청년 |
|---|---|---|
| 지역 필터 | **정확** — 익산 52건 전부 익산시, 오염 0 | **깨짐** — 익산 조회에 경상북도 의성군 6건 혼입 |
| 나이·날짜 | 자유 서술 (`"2026년 상반기"`, `"만 19~34세 이하*"`) | **구조화** (`"20260415 ~ 20260930"`, `sprtTrgtMinAge: 19`) |
| 인증키 | 자동승인, 무료, 일 10,000건 | 담당자 승인 심사 |
| 맡은 일 | 익산에 **새 사업이 등록되면 포착** | 기존 정책의 **값 어긋남 대조** |

## 하는 일 세 가지

### 1. 3자 대조 — 앱 · 온통청년 · 보조금24

2자 대조는 어긋남을 찾아도 **어느 쪽이 낡았는지 모른다**
(`scripts/fetch-youth-policies.mjs` 의 `findMismatches` 주석이 인정한 한계다).
3자면 갈린다.

- **우선순위 높음** — 바깥 두 소스가 서로 같고 앱만 다르다. 앱을 먼저 의심한다.
- **우선순위 낮음** — 앱이 한쪽과 같다. 바깥 한 곳이 낡은 흔한 경우다.
- **대조불가** — 바깥이 그 값을 말하지 못한다. **일치로 세지 않는다.**
  아무도 확인하지 않은 값이 확인된 값처럼 보이면 안 된다.

정책명은 표기 차이를 정규화해서 비교한다. 앱은 이름에 팀 주석을 단다 —
`"청년월세 지원 (2026년 상시사업 전환)"` 대 `"청년월세 지원"`. 괄호와 공백만
걷어내고 그 이상은 뭉개지 않는다 (`"파주시 청년월세 지원"` 은 다른 사업이다).

### 2. 익산 주거 목록 감시

보조금24 에서 `소관기관명 LIKE 익산` + `서비스분야 LIKE 주거` 를 훑어
신규·변경·사라짐을 잡는다. 자유 서술 텍스트는 **파싱하지 않고 지문(해시)만
비교한다** — 해석은 사람이 하고, 기계는 "바뀌었다"만 말한다. 공백 차이는
정규화해서 편집 흔적으로 알림이 울리지 않게 한다.

2026-08-30 기준 익산 `주거·자립` 은 8건이고 그중 청년 현금성 지원은 사실상
없다. **0건이어도 감시는 의미가 있다** — 등록되는 순간 잡는 것이 목적이다.

### 3. 정책 요건 변경 (온통청년)

3자 대조는 정책명·신청기간·나이 **다섯 필드만** 본다. 소득·재산·제출서류·중복수급
조항은 자유 서술이라 값으로 비교할 수 없다.

    earnEtcCn: "청년가구 - 중위소득 130% 이하 / 원가구 - 중위소득 100% 이하"

그래서 보조금24 텍스트와 같은 방식으로 **지문만 뜬다.** 바뀌면 알리고, 무엇이
어떻게 바뀌었는지는 사람이 원문을 본다.

> [!NOTE]
> 이 감시는 2026-08-30 에 생겼다. 익산형 청년월세의 원가구 소득 요건이 앱에 아예
> 없다는 것을 사람이 60개 필드를 손으로 뒤져서 찾았고, 주간 점검은 그걸 못 잡았다.

지문에는 **요건이 적힌 필드만** 넣는다. 레코드 전체를 넣으면 조회수(`inqCnt`)와
수정시각(`lastMdfcnDt`)이 매주 바뀌어 헛알림이 울리고, 그러면 아무도 보고서를 안 본다.

### 4. `verifiedAt` 낡음

대조한 지 90일이 넘었거나 아직 `null` 인 정책을 알려준다.

## 설정

저장소 Secrets 에 두 개를 넣는다 (Settings → Secrets and variables → Actions).

- `BOJOGEUM_KEY` — [공공데이터포털 15113968](https://www.data.go.kr/data/15113968/openapi.do)
  활용신청(자동승인) 후 마이페이지의 **일반 인증키(Decoding)**
- `YOUTH_API_KEY` — [온통청년 OPEN API](https://www.youthcenter.go.kr/myPage/openapi), 담당자 승인 심사

로컬에서 돌릴 때는 `apps/web/.env.local` 에 같은 이름으로 넣는다 (`.env*` 는 gitignore 됨).
**키가 없으면 그 소스를 건너뛰고, 건너뛰었다는 사실을 보고서 맨 위에 적는다.**
조용히 넘기면 "확인했는데 문제 없음" 으로 읽히기 때문이다.

## 종료 코드

| 코드 | 뜻 | 워크플로 동작 |
|---|---|---|
| 0 | 검토할 것 없음 | 이슈를 만들지 않는다 |
| 10 | 검토 필요 | 보고서를 본문으로 이슈를 연다 |
| 그 외 | 실행 실패 | 워크플로가 실패한다 |

## 스냅샷을 왜 별도 브랜치에 두는가

`develop`·`main` 은 PR 필수에 푸시 허용자가 제한돼 있어 워크플로가 직접 올릴 수 없다.
스냅샷(익산 목록 + 온통청년 요건 지문)은 보호되지 않은 `freshness-snapshot` 브랜치에 파일 하나(`freshness-snapshot.json`)로 두고
매 실행마다 force-push 한다. 저장소 본체에는 커밋하지 않는다 (gitignore).
